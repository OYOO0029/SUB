## 계정과 데이터

- 가계부와 같은 이메일/비밀번호로 앱 안에서 로그인합니다. GitHub Pages는 공개 화면만 제공하고, 개인 기록은 인증 후 읽습니다.
- 노션·다른 브라우저는 각각 로그인해야 할 수 있습니다. 로그인 세션 자동 공유(SSO)는 아니며, 같은 계정의 기록을 동기화합니다.
- Supabase 프로젝트: vxwvlqrqatkvuvpxozob. 기존 spending_state 테이블의 사용자별 행을 사용합니다. 가계부는 state.mySpendingV1, 일정은 state.myWeekV1에 구분합니다.
- 저장 직전에 서버의 전체 JSON을 읽고 일정 영역만 교체합니다. updated_at 조건으로 동시에 바뀐 행을 덮어쓰지 않습니다. 기존 가계부 및 다른 필드는 보존합니다. RLS 설정과 공개 접근 범위는 변경하지 않았습니다.
- Realtime 알림 및 15초 주기, 화면/온라인 복귀 때 서버를 확인합니다. 편집창이 열려 있으면 수신 반영을 기다립니다. 두 기기의 일정 수정이 겹치면 자동 덮어쓰기를 중단하고 사용자가 기록을 선택합니다.

## 기존 일정 보존

- myWeekPlanner_v5, myWeekPlanner_v1, 이전 보호 백업/미전송 데이터는 삭제하지 않습니다.
- 소유자가 확인된 동일 계정 캐시만 자동으로 읽습니다. 소유자 미확인 기존 기록은 로그인 후 ‘이 기기의 이전 기록 가져오기’로 명시적으로 가져옵니다. 서버로 반영하려면 ‘현재 데이터로 연결’을 선택합니다.
- 예전 프로젝트에만 저장된 기록은 해당 프로젝트를 복구하거나 JSON 백업을 가져와야 합니다. 프로젝트 연결 변경만으로 접근 불가능한 서버의 기록이 자동 이전되지는 않습니다.
- 로그아웃하면 개인 일정과 편집 초안을 화면에서 지웁니다. 캐시와 백업은 프로젝트/사용자별로 구분하여 보관합니다.
- 저장소 제한 시 메모리로 로그인·동기화가 가능합니다. 이때 창을 닫기 전에 ‘동기화됨’을 확인해야 하며, 다음 방문에는 다시 로그인할 수 있습니다.

## 유지보수

- schedule.html: 일정 화면, 편집, 데이터 연결부

- schedule-cloud-ui.mjs / schedule-cloud-core.mjs: 가계부와 동일한 인증·조건부 동기화 구조

main에 배포하면 기존 URL을 사용하는 노션 임베드에도 새로고침 후 업데이트가 반영됩니다. 새 배포에서 저장소 키·서버 슬롯 이름을 임의로 변경하지 마세요. 기존 SQL 파일은 과거 my_week_state 테이블용으로 현재 통합 구조에 실행할 필요가 없습니다.

## 검증

npm install 후 npm test (Node 24 기준). 개발 의존성은 jsdom이며 SDK는 번들에 포함되어 별도 다운로드가 필요하지 않습니다.

자동 검증: 저장소 차단/권한 회수, 계정 전환, 기존 캐시 수동 이전, 미전송 복구, 가계부 필드 보존, 두 화면 동기화, 로그인 오류, 세션 복원 시 사용자 검증. 이전 공유 엔진 테스트도 함께 유지합니다.

브라우저 검증: node tests/schedule-preview.mjs 실행 후 127.0.0.1:4175/schedule.html 및 localhost:4176에서 확인합니다. 가상 계정 a@example.test / b@example.test, 임의 테스트 비밀번호를 사용합니다. 이 서버는 SDK와 API를 모형으로 대체하며 Supabase에 연결하지 않습니다. 저장·새로고침·다른 화면 수신·저장소 차단 iframe·로그아웃을 확인했습니다. 기존 schedule-sync-browser.cjs는 통합 전 구조의 참고 테스트이며 현재 브라우저 검증에는 사용하지 않습니다.

실제 서버 읽기 전용 점검: Auth 설정 HTTP 200, 이메일 로그인 활성화, 비로그인 테이블 조회 HTTP 401/42501. 사용자의 실제 비밀번호로 로그인하거나 실제 기록을 수정하는 검증은 수행하지 않았습니다.
